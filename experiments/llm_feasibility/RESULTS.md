# 2A.0 Local LLM feasibility: results (2026-11-26)

Protocol and selection criteria: `docs/PHASE2_PLAN.md` §2A.0. They were pre-registered in commit `02e51b3` before any model run. Configuration: `config.json`. Numbers: `results/summary.json`, generated by `analyze.py` from every raw log; no run was excluded. These measurements are separate from the synth_v0 benchmark and are not comparable with it. No held-out (T5–T8) scenario was used.

- local inference;
- native structured tool calls;
- JSON/argument parsing;

## Deviations from the protocol (disclosed)
- **Crashed first attempt.** The first Stage A attempt for Qwen3-1.7B crashed while shutting down the memory sampler: a thread attribute name clashed with a private method of `threading.Thread`. The checks and the T1 run had executed, but the crash happened before the log was written, so no raw file exists and nothing from it is counted. Stage A was rerun after the fix. The fix did not change any measurement logic.
- **Safety amendment** (made before Qwen3-4B Stage A and recorded in `config.json`): a watchdog aborts a run after 15 consecutive seconds of critical pressure. It is not a selection criterion, and it never fired.
- **Cosmetic changes after the runs.** `run.py` was reformatted and given a lint-suppression header after the runs; its AST is unchanged (hash `6bec6fac942367f5` before and after).

## Criteria and stop rules
- **Stage B stop rule** (swap growth > 1.5 GB): **triggered for both models** (1.7B +1,540 MB; 4B +2,833 MB). Stage C was therefore not run. The criteria were not relaxed.
- **Selection criteria:** S1–S4 are defined on the Stage C population, so formally they are **not evaluated**. The pilot indicators below are not a substitute.

## Findings
1. Both models produce syntactically valid native tool calls after one bounded retry, but **syntactic validity says little about correctness**. Qwen3-1.7B followed the call sequence and ignored the policy rules on every task.
2. Qwen3-4B-Instruct-2507 applied the rules correctly in 4/5 pilot runs. It is fast enough (warm median 1.6 s per decision), and its prompts stayed far below 4096 tokens.
3. **Memory is the blocker on this machine as configured.** The system was already at warning pressure with about 5 GB swapped before any model loaded. Loading 3.2 GB (4B) or 1.5–1.7 GB (1.7B) pushed swap up by 1.5–2.8 GB and caused intermittent critical pressure.
4. Fixed seeds were sent, but nothing here demonstrates determinism (n = 1 per template and temperature).

## Proposed reduced protocol 2A.0b (needs approval; criteria unchanged)
1. **Controlled environment.** Quit non-essential applications before the run. Record a 60 s baseline; proceed only if no sample is critical and swap is stable.
2. **Memory-reducing configuration**, each measured in Stage A only and pre-registered before running:
   - (a) `num_ctx` 2048 (max observed prompt 1,258 tokens; the guard aborts at 1,843);
   - (b) Ollama server flags `OLLAMA_FLASH_ATTENTION=1` and `OLLAMA_KV_CACHE_TYPE=q8_0`. This changes your Ollama app's environment and needs a restart, so it needs your approval.
3. **Qwen3-4B-Instruct-2507 only.** Stage B, then a reduced Stage C: T1–T4 × t ∈ {0, 0.7} × 5 = 40 runs (about 10–15 min at the measured speed).
4. **Fallback candidates** as a separate, later experiment: no ≤ 2 GB model has shown adequate semantics yet. Options are Phi-4-mini-instruct (MIT, similar size), a lower quantization of Qwen3-4B (quality risk), or llama.cpp `llama-server` with explicit memory settings.
